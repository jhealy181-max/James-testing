What the demo must prove

Five things a senior audience should see in ten minutes

The proof of concept isn't a prototype of every feature. It is built to make the Stage 1 strategy tangible and to test the hypotheses behind it.

1 · Decision network

Evidence, peers and the room in one place

A leader lands on a home page showing their next Circle session, an open Pulse, pending introductions and the next QS summit, not a list of articles.

2 · Give to get

Pulse results unlock after contributing

An institution answers five recruitment questions, then sees peer benchmarks. Groups smaller than five are hidden.

3 · Live QS evidence

Global Student Flows, read from qs.com

The mobility hub shows the three scenarios, key published figures and page excerpts, each marked live or saved, with the date.

4 · Two paying sides

Partners in a space members control

A partner publishes labelled briefings, responds to member challenges and sees aggregated priorities, with no contact unless the member opts in.

5 · Tiers that mean something

Access rules enforced on the server

Switching to a Network-tier institution visibly locks Circles and cohort cuts. The rules live in the API, not just the screen.

6 · Summits as heartbeat

Convene links the calendar to the network

Mark attendance, get suggested meetings, and reserve closed roundtables, which follow on in Circles afterwards.

The Replit approach

Upload, press Run, open the link

The main requirement is that someone without coding knowledge can run it first time. That drives three design choices.

  1. Upload the ZIPOpen replit.com/import, choose ZIP file, and upload qs-one-replit.zip.
  2. Press RunThe .replit file tells Replit to use Node 20 and run npm start on port 3000.
  3. Use the appIt opens in the Webview. Demo data is created automatically on first run, and QS pages are read in the background.

Front end already built

The React app is built into public/ before zipping, so Replit has no build step to fail. The source is included for anyone who wants to edit it.

No runtime dependencies

The server uses only Node's standard library (HTTP, file system, fetch). There is no npm install to wait for or break.

Self-contained data

A JSON-file database is created and seeded on first run, and reset from the team console. There is no external database or API key.

QS content & scraping

Reading QS pages responsibly, starting with recruitment

The source service reads 21 public qs.com pages plus the QS Insights listing. The recruitment (mobility) domain is the deepest: it covers Global Student Flows, the International Student Survey, recruitment datasets, market reports and a case study.

Recruitment sources
  • QS Global Student Flows report and framework hub
  • Global Student Flows: UK, US, Europe, Australia & New Zealand
  • QS Student Recruitment Datasets
  • QS International Student Survey, plus the China insight
  • UK recruitment and US 2026 market insights
  • Global Student Flows recruitment case study
  • New QS Insights articles, classified by keyword
Rules the reader follows
  • Public pages only; checks robots.txt first
  • One request at a time, with a pause; 15-second timeout
  • Keeps the title, description, headings and up to five short excerpts, with a link back
  • Never copies whole pages or licensed datasets
  • Every item carries its read time; the app shows live, stale or saved
  • Runs on start-up, every 12 hours, and on demand

● Live from qs.com

Read successfully. Shows "Live from qs.com · 2 h ago".

● Last read, refresh failed

Was live before; the latest attempt failed. Shows the last good date.

○ Saved copy

Never read live on this server. Shows a saved summary dated 24 Sep 2026.

Two caveats. This build environment could not reach qs.com (its network policy blocks the site), so live reading was tested for failures only. The parser was tested on sample pages, and the saved copies were prepared from QS's public pages via search. On Replit the reader should work. If qs.com refuses automated requests, the app keeps working on saved copies and the Sources page says so. QS pages also showed different dates for the Middle East summit, so the demo flags "check date".
Published figures used on screen: the three Global Student Flows scenarios; about 4% annual growth in demand and about 8.5 million mobile students by 2030; 80+ markets and 15 drivers; and ISS findings such as "45% consider four or more universities". Each figure links to its QS page. Market-level forecasts stay in the licensed QS Student Recruitment Datasets.

Data & API

What is stored and how the screens get it

Data model

  • Institutions: tier, region, type, priorities, challenges, "open to", visibility, verified
  • People: organisation, role family, interests, regions, partner-contact opt-in, digest preference
  • Partners: package tier, sector, domains, offers
  • Circles: type, minimum tier, invitation-only, members, sessions
  • Posts and replies (Exchange and Circle discussion)
  • Pulses, questions and responses (one per institution; demo responses flagged)
  • Events, roundtables, introductions, challenges and proposals
  • Activity log; source cache with read times and errors

API (all JSON)

  • GET /api/bootstrap: person, access, network
  • GET /api/feed, /api/briefings/:id, /api/domains/:id
  • GET /api/sources, POST /api/sources/refresh
  • GET|POST /api/posts, replies, upvote
  • GET /api/pulses/:id?region=&type=, POST …/responses
  • POST|DELETE /api/circles/:id/join, request
  • POST /api/intros, PATCH /api/intros/:id
  • POST /api/events/:id/attend, GET …/matches, roundtable RSVP
  • Challenges, proposals, GET /api/partner-insights
  • PATCH /api/me, /api/institutions/:id; team overview and reset

Extending it

A starter prompt for Replit Agent or Claude Code

To change the demo without coding, paste a request like this into Replit's AI assistant. It keeps the build's guardrails in place.

This is the QS One proof of concept (Node server in /server with no dependencies, React source in /client, built output in /public). Keep these rules: - Do not add runtime npm dependencies to the root package.json. - After changing /client, run "npm run build" so /public is updated. - Enforce any new access rule in server/index.js, not only in the UI. - Label every content item with its source and date; never present saved content as live. - Keep all institutions, people and partners fictional. Change request: [describe the change, e.g. "add a fourth Pulse on TNE partner selection with five questions and demo responses from six institutions"].
